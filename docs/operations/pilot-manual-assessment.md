# Manual assessment of the first-party login pilot

This pack prepares the outstanding **T021 / LOGIN-007 and LOGIN-009 / US2 AC4** assessment. It contains instructions, **not executed results**. The [current acceptance matrix](../../specs/004-first-party-login/acceptance-matrix.md) distinguishes existing automation from open human acceptance. Use the [result template](../../specs/004-first-party-login/manual-assessment-results.md) for each assessment session.

The scope is the Development-only, synthetic, non-administrator Razor login and its error/continuation states. Admin BFF, React, MFA, recovery, consent and production rollout are outside this pilot assessment. The implemented administrator MFA/recovery pages have a separate [manual assessment packet](administrator-manual-assessment.md). The future five-minute application-creation target in **NFR-09** cannot be measured using this pilot. A qualified assessor must evaluate the applicable **WCAG 2.2 Level A and AA** criteria across the complete scoped process; the cases below are a starting inventory, not a complete WCAG checklist or conformance assertion.

## People and environment required

An engineer provisions the isolated environment and relying party; a tester records reproducible observations; a qualified accessibility assessor owns the scoped accessibility disposition. One person can perform multiple roles if their competence and scope are recorded. A user's initial checks are useful defect evidence but do not automatically establish a qualified review. Named assessors remain pending.

Run .NET, Docker and Aspire in the WSL2 Linux distribution as described in [the pilot runbook](first-party-pilot.md#windows-with-wsl2), using the pinned SDK and providers. Use a **Windows browser and Windows assistive technology** for the proposed human sessions. Record actual Windows/WSL, browser, extension, screen-reader and database versions. Linux Playwright WebKit is not Windows Safari, and automated CI evidence is not manual Windows evidence.

Provision the pilot's external issuer credentials and protected key ring through [issuer protection](issuer-protection.md), then follow [enable and initialize](first-party-pilot.md#enable-and-initialize). Use only new synthetic account/client credentials and disposable databases. The default AppHost has health endpoints only. Never place private keys or secrets in the repository, command arguments, screenshots or shared logs. Stop and diagnose trust or bootstrap failure; do not bypass TLS or repair protected records manually to continue an assessment.

### Interactive relying party is a prerequisite

**This repository currently does not ship an interactive test client.** The automated fixture's server is not a persistent manual application. Before testing, the engineer must supply and review an HTTPS, server-side OpenID Connect client with the following configuration. If none is available, record `blocked: interactive relying party unavailable`; do not instruct a tester to open a nonexistent demo URL. Building a reusable manual client would be a separately planned implementation with its structure confirmed first.

| Client setting / behavior | Required value or constraint |
| --- | --- |
| Authority | Exact resolved AuthServer HTTPS issuer, obtained from the enabled Aspire environment and verified against discovery; do not assume its dynamic port. |
| Client ID | `identityplatform-pilot` |
| Client secret | The privately provisioned `Pilot:ClientSecret`, held only by the server. |
| Callback | Exactly `Pilot:RedirectUri`: canonical HTTPS URL without user info, query or fragment. Use a separate host from the issuer (the fixture uses `127.0.0.1` versus `localhost`) to preserve host-only cookie separation. |
| Flow | `response_type=code`, `response_mode=query`, scopes `openid pilot_api`, fresh S256 PKCE verifier/challenge for every request, token endpoint `client_secret_basic`. |
| Client validation | Server-held fresh state, nonce and verifier; state is single-use, expiring and bound to the initiating browser session, with independent outstanding correlations for tabs. Validate state and independently validate returned ID-token signature, issuer, audience, nonce and lifetime. Do not assume a callback means authentication passed. No UserInfo, refresh, PAR or logout calls: these are not implemented in this pilot. |
| Browser interaction | A client start action; fresh-login action using original `prompt=login` (or `max_age=0`); callback that exchanges once, then redirects to a clean result page showing a generic success/failure only. Client must retain multiple outstanding requests for the two-tab case. |
| Secrecy and failure | Tokens remain server-side; never show tokens, secret, state, verifier or code in the result page, browser storage, logs or traces. Code/state necessarily arrive in the protocol callback URL; remove them from the displayed URL before recording observations. A lost exchange response starts a new flow, not a retry. |

TLS must be trusted independently by the WSL client process and Windows browser, for both issuer and callback hosts. Import only the public development certificate according to local policy; do not transfer an issuer private PFX for browser trust. Preserve CSP, antiforgery, cookie, issuer and audience validation. Record the supplied client's name, exact release/build and source revision (or vendor build identifier), separately from an opaque local configuration reference and engineer sign-off. Both product and client revisions are required to attribute findings and reproduce retests; do not copy secret configuration into a result file.

### Preflight before each provider session

1. Record the exact tested product commit and whether its working tree is clean, plus the supplied client's identity/build/source revision and private configuration reference. Start the disposable `PostgreSql` or `SqlServer` profile; confirm Migrator and pilot bootstrap completed and AuthServer is ready. Record startup failures as blocked observations.
2. Create an isolated browser profile and a disposable password-manager vault/profile using synthetic credentials only. Do not import or sync a personal vault. Avoid captured browser/network traces; use sanitized written observations. An OS clipboard manager or password manager may retain copied test credentials; clear/dispose them after testing.
3. Confirm the Windows browser reaches the issuer and callback with normal certificate validation and no warnings. The dashboard URL is not the issuer/client URL. Do not browse directly to `/account/login` as a normal sign-in start; it requires a bound authorization interaction.
4. From the reviewed client, start a fresh request, complete the protected form and verify the clean, server-validated success result. Confirm a fresh-login request displays the form again. If this control fails, stop the assessment and distinguish issuer, client, TLS and environment causes.
5. For each case use a new client request with `prompt=login`, unless its steps explicitly say otherwise. Complete flows sequentially except the specified two-tab case. Interactions expire after five minutes; account failures lock out after five invalid attempts. Keep wrong-password probes below that threshold; use a deliberately recreated disposable environment if lockout interferes, never an undocumented database repair.

## Proposed execution matrix

The assessor records the exact selected tools/versions before execution and signs off their coverage rationale. These are recommended starting cells for the user's Windows/WSL2 environment, not verified compatibility or a new product support policy. Run each selected cell separately on **PostgreSQL and SQL Server**; preserve any unrun provider as a gap.

| Cell | Windows tooling | Manual focus |
| --- | --- | --- |
| W1 | Current stable Edge (Chromium) + NVDA | Keyboard, speech/browse/forms modes, errors, themes and reflow. |
| W2 | Current stable Firefox + NVDA | Independent browser/assistive-technology behavior for the same states. |
| W3 | Edge built-in password manager in an isolated profile | Save/autofill and paste through genuine fresh sign-in and error recovery. |
| W4 | Firefox + an assessor-selected independent password manager (for example Bitwarden with a disposable vault) | Extension integration, matching origin and username/current-password fields, autofill/paste and error recovery. |

Do not install a personal/cloud vault or paid tool as an implicit prerequisite. Record unavailable tools as blocked and have the qualified assessor agree and document alternatives before relying on replacement evidence. Record Windows high-contrast/forced-colors and browser zoom settings. A suitable macOS/Safari/VoiceOver session, touch/physical mobile coverage and other assistive technologies need their own environment and assessment rationale; WSL2 cannot establish those observations. The full accessibility assessment identifies remaining platform coverage rather than treating this proposed matrix as exhaustive.

## Manual cases and expected observations

Run PM cases in W3/W4, SR cases in W1/W2, and the remaining cases in all applicable selected cells. Cover both providers. Light, dark and system-selected light/dark appearances apply to valid form, error, unavailable and continuation states. Repeat relevant visual/keyboard observations at desktop and a 320 CSS-pixel viewport; also examine 200% text resize and 400% zoom on a suitable desktop viewport. Record actual viewport/scale rather than equating an emulated viewport with a real mobile device.

| ID / requirement | Procedure | Expected observation and evidence |
| --- | --- | --- |
| MAN-01 / LOGIN-007, FR-19 | Begin a fresh form. Using only Tab, Shift+Tab, Enter and Space, use the skip link, theme selector, fields, password visibility button and submit. Repeat after a generic credential error. | Logical order; visible, unobscured focus; skip link reaches main; every applicable control operable without a pointer or trap. Labels and client context remain understandable. Record actual focus sequence and any loss of focus. |
| SR-01 / US2 AC4, NFR-09 | With screen reader enabled, navigate landmarks/headings and controls in browse and forms modes. Inspect page title, username/password labels, required state and password visibility action; submit an empty form, then one wrong password. | Name/role/value and required/validation information are understandable without vision. Generic server error is discoverable/associated with fields; focus/announcement enables recovery. Record the observed announcement and focus, not just “accessible.” Do not include the credential in a transcript. |
| SR-02 / LOGIN-004/007 | In a fresh request complete login, observe automatic continuation and clean client result. In another fresh request disable JavaScript **before** opening the form, complete it and follow `Continue to application` by keyboard/screen reader. | Completion remains operable and understandable; no redirect loop or inaccessible dead end. Without JavaScript, optional theme/visibility controls may be absent, but credential entry and the continuation link must work. Separate the issuer's announcement from the supplied client's result-page behavior. |
| PM-01 / US2 AC4 | Using the actual password manager, save the synthetic login for the issuer origin. Begin another fresh request, select that entry, autofill and submit. Repeat with a new isolated browser session. | Manager recognizes username/current-password fields and correct origin; valid autofill completes the protected flow. Record whether save/autofill was offered or required explicit selection, and actual completion. Field attributes or Playwright fill are not password-manager evidence. |
| PM-02 / US2 AC4 | Paste a synthetic password from the test vault; toggle Show/Hide using keyboard; submit one wrong password, then explicitly refill the correct credential and submit. | Paste works; visibility action has a meaningful accessible state/name. A failed response does not echo the submitted password. Distinguish a manager's deliberate refill from server echo; repeat with autofill temporarily disabled to confirm the returned field is empty. Record generic error and recovery without capturing field contents. |
| MAN-02 / LOGIN-007, FR-19 | Check each appearance and state at desktop/320px, text resize/zoom and Windows forced-colors. Change the OS preference with System selected; inspect page load as well as subsequent changes. | No lost text/action, overlap or avoidable two-dimensional scrolling for this simple form; focus, errors and controls remain distinguishable. Assessor measures applicable text/non-text contrast and target/focus requirements, recording method and values. Theme alone is not sufficient evidence. |
| MAN-03 / LOGIN-003/007 | Submit one wrong password and, in a separate new request, an unknown synthetic username. Recover through a new valid request. Avoid the five-failure lockout threshold. | Same generic account-disclosure-safe error; usable error recovery and understandable labels/focus; no credential echoed or included in result evidence. A difference caused by the supplied client is attributed explicitly. |
| MAN-04 / LOGIN-004/007 | Open a new form and leave it idle beyond the five-minute interaction expiry before submitting. Separately revisit a completed form using Back/refresh. Start a new flow from the client to recover. | Terminal/generic unavailability is understandable and leads the user back to a fresh client start, never a second authentication through the stale form. Record actual wording and navigation. Do not edit interaction URLs or database state to simulate time in a manual observation. |
| MAN-05 / LOGIN-004/007 | Start two fresh client requests in separate tabs before completing either. Complete one, then the other, observing labels, focus and each clean client result. | Both initial forms remain separately operable; no mistaken tab/client context or user confusion hidden by automation. Use the automated security matrix for internal subject/session invariants; the assessor records actual usability and any unexpected denial. A client unable to retain two correlations blocks this case rather than proving an issuer defect. |
| MAN-06 / LOGIN-007/009 | Complete the valid and error-recovery journeys without coaching after the setup briefing. Record confusing wording, navigation or assistance needed; optionally measure elapsed time and the exact start/finish definitions. | Observable usability issues are reported. There is no invented pilot-login timing pass threshold. The approved five-minute trained-administrator application-creation criterion remains unexecuted in M09-A. |

The qualified assessor additionally inventories all rendered states and evaluates every applicable WCAG 2.2 A/AA success criterion, including timing, accessible authentication, text spacing, focus appearance/visibility and errors. Record criterion-level applicability, method, outcome and rationale; `not assessed` is not `not applicable`. Review the whole scoped process, including boundaries to the supplied client, while clearly attributing external-client findings. A small scenario table, a screenshot, scanner output or an AI opinion cannot establish complete WCAG conformance.

## Evidence, findings and closure

Copy the [results template](../../specs/004-first-party-login/manual-assessment-results.md) to a restricted local work location. Record only synthetic run/case IDs, exact revision/tool versions, provider, observed behavior, status and sanitized evidence references. Keep raw recordings locally access-controlled if the assessor needs them; do not upload HAR, browser profiles, vault exports, logs with callback URLs, credential fields or private keys. Public repository evidence should be reviewed summaries and empty-page/cropped UI observations only. Agree retention and disposal with the evidence owner; do not invent a legal retention period.

Use `passed`, `failed`, `blocked` or `not_run` for cases. A pass needs an actual observation and assessor; blank rows remain unrun. Log defects with a safe reproduction, severity, owner, affected requirement, observed versus expected behavior, and restricted evidence pointer. Diagnose an external client's failures separately. The engineer fixes confirmed defects and adds appropriate automated regressions; the human assessor reruns the affected cases and relevant neighboring states on the fixed revision. Retain initial failures and retest lineage, rather than replacing them with a green summary.

T021 remains open until the agreed scoped manual matrix and qualified accessibility assessment have usable results, findings are resolved/retested, and the implementation lead reconciles those results with the full automated matrix and independent reviews on the accepted revision. Unrun requirements, omitted environments and incomplete WCAG criteria stay visible. A material exception requires a concrete approved amendment; this document grants none. T021 completion still would not complete M01-E, M01-F, administrator application-creation usability or public-release certification. All ASVS rows remain `pending/not_assessed` unless their own qualified evidence changes that status through the assurance workflow.
