## Proposed graph and canonical transport

Reuse the existing production AppHost graph in Aspire.Hosting.Testing. The test builder adds `auth-secondary`, another `Projects.IdentityPlatform_AuthServer` resource. Both nodes depend on the same completed migrator and pilot bootstrap and receive the same least-privileged platform connection, provider, canonical issuer and durable protection settings. Secret references remain secret ParameterResources. Do not copy administrator database connections into either node. Bootstrap executes once; no seeding repairs state between node transitions.

Keep `auth`'s allocated HTTPS origin as the one canonical issuer. Keep the RP HTTPS origin and exact registered callback stable. Each node has a distinct allocated loopback HTTPS transport endpoint, an actual distinct AuthServer child process and normal readiness checks. Retain the original material directory, populated encrypted DP ring, signing/encryption/wrapping keys and database containers throughout.

The recommended test-only routing adapter uses immutable per-node `SocketsHttpHandler` instances with `ConnectCallback`. The request URI, Host header and TLS server name remain those of the canonical HTTPS origin; only the destination loopback socket changes to the selected Aspire node. Use the trusted Development certificate normally. No custom certificate acceptance callback, disabled TLS/issuer validation, forwarding middleware, caller-controlled node header, fallback destination, retry policy or production proxy setting is permitted.

Return a raw TCP NetworkStream from ConnectCallback, allowing SocketsHttpHandler to perform TLS. An outer handler validates every request and each bounded redirect, including requests that reuse an existing connection; ConnectCallback alone is not an origin guard. The selector accepts only the exact canonical issuer origin and exact RP origin. RP requests connect directly to their registered loopback endpoint. Reject other schemes, hosts or ports before a socket is opened. Disable environmental HTTP proxies and require HTTP/1.1 exactly so an HTTP/3 transport cannot bypass the TCP selector. Include an actual untrusted-certificate rejection through this adapter. Each node's connection pool is private and immutable; a mutable selector behind pooled connections cannot establish node affinity. Share the original CookieContainer deliberately between the separate browser clients when moving browser state. Backchannel token exchange and metadata fetches must also use an explicitly selected node; the existing RP's default backchannel cannot silently route an assertion to the primary node.

Automatic redirect navigation is allowed only for setup where the existing genuine form helper already expects it. Continuity and denial assertions use bounded manual navigation with exact origin/path allowlists. A client-side dispatch claim alone is not proof of server handling: record the canonical Aspire endpoint and selected process-owned listener separately, require distinct node listeners/processes, and exercise pinned requests while the opposite node is stopped. No production endpoint may echo process identity or sensitive request data merely for testing.

## Process and resource proof

Before test use, require healthy notifications belonging to each current process generation and an actual HTTPS readiness response on each pinned transport. Capture launcher PID/start time and the actual AuthServer descendant PID/start ticks with the existing process-tree helper. Reject shared/stale process identity. Resolve the direct node transport from the captured child’s owned socket descriptors and Linux TCP/TCP6 LISTEN rows: require exactly one loopback application port, unchanged process generation around the read, and no unrelated/wildcard listener substitution. This port is distinct from Aspire’s external proxy port. Re-resolve after replacement and discard old clients; do not mutate an existing connection pool. Collect generations in the existing synchronized lifecycle recorder, including failed starts, and attempt every teardown stage under the existing bounds.

When stopping a node, require the stop command, terminal Aspire state and termination of all captured descendants. While it is stopped, an explicitly pinned request must fail; an eligible original-cookie request on the survivor must succeed without login fallback. Start only the stopped node again and require a genuinely new generation and fresh readiness. Confirm unchanged issuer/callback, database identities, completed one-shot jobs and material hashes. Do not retry an ambiguous code redemption through the surviving node.

## Native state, concurrency and bounded failure

Use existing Identity/OpenIddict managers and native entries for setup/verification; test observations never redeem tokens directly or replace HTTP decision-making. Isolate global eligibility mutations from other cases. Restore with an independent bounded cancellation token even when the assertion fails. If restoration, process control or capture fails, invalidate the environment and fail subsequent dependent cases closed.

The code lifetime stays 60 seconds. Prepare browser/session cohorts before code issuance; capture original entry expiration and require more than ten seconds remaining before a live success/race assertion. No replacement code, refreshed login or reset TTL may rescue a failed continuity test. Report latency as a test observation, not an availability SLA. No blanket retries, sleeps that hide timing failures or relaxed protocol error predicates.

Concurrent redemption must use distinct node connections and a rendezvous that confirms both participants are ready before release, with bounded cancellation/drain on failure. Native persisted consequences are checked only after both responses finish. If the native library permits a documented race outcome incompatible with exactly one winner/revocation, stop and document the demonstrated defect; do not broaden the expected result to make it pass.
