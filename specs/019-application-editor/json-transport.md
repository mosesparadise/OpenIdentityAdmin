## Implemented boundary

It authenticates the current protected cookie and durable browser/ticket association, disposes the read scope, and uses native ASP.NET antiforgery to issue only `requestToken`. Tokens have a separate application purpose and bind the browser digest and generation. They cannot substitute for login/logout or logout-reconciliation tokens. The native header is `X-CSRF-TOKEN`; existing form-only login/logout admission explicitly rejects that header. The paired cookie retains its host-only, Secure, HttpOnly, Strict configuration. Acquisition does not renew durable session state or return OAuth credentials.

The create/edit/replacement handlers enforce exact configured origin, exact raw route, finite methods, no browser bearer, no query, reviewed JSON media/framing, one bounded native CSRF header and one canonical strong precondition. Missing versions return 428; malformed versions return 412. Actual input is capped at 32 KiB before strict duplicate/unknown/required-field parsing and Core validation. Validated original UTF-8 bytes are retained rather than reserialized, avoiding Unicode escape expansion beyond the input limit.

One fixed HTTPS client sends only the code-owned method/path, protected server bearer, content headers and validated If-Match. It has no redirects, cookies, automatic retries or arbitrary header/destination forwarding. Actual response bytes remain capped at 512 KiB. The response must match the finite DTO, managed profile, exact application ID/ETag binding, submitted fields/expiry, and the exact next revision for edits/replacement. Only creation/replacement may return the bounded canonical native-generated secret. Upstream error bodies, private headers and cookies are discarded.

The original five-second budget covers input, session reads, native validation, network work and publication. Every Sessions read scope disposes before network dispatch. A fresh final durable read suppresses output if the browser generation or credential changed while the upstream request ran. Frozen original deadlines are checked again after serialization, immediately before publication. Lost output, cancellation or changed generation does not imply remote rollback and never causes a retry.

Production write routes remain unmapped until T009/T016 provide their actual API operations. Tests explicitly map the same handlers against a controlled upstream response seam.
