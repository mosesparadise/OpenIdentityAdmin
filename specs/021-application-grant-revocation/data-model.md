# Grant revocation data model

All tables belong to the existing Platform store and have additive provider migrations.
No native Identity/OpenIddict columns or prior migrations change. ReplayUntil bounds only
idempotency recovery: it never expires accepted batch authority or renews MFA.

| Entity | Fields and constraints |
| --- | --- |
| ApplicationGrantJob | UUID Id; exact ApplicationId max 400; State integer 1 queued, 2 processing, 3 stopped, 4 succeeded; Failure integer 0 none, 1 authority, 2 target, 3 storage, 4 clock; Revision positive concurrency token; AuthorizationCount/TokenCount nonnegative 64-bit; CreatedAt/ObservedAt nonnegative UTC seconds with ObservedAt >= CreatedAt; EffectiveApprovalId UUID; original disabled application revision positive. |
| ApplicationGrantApproval | UUID Id; required JobId FK restrict; ActorId max 450 (no user FK so deletion preserves audit); Action integer 1 submit, 2 continue; Reason integer 1 maintenance, 2 security, 3 configuration; RequestKey UUID; RequestHash generated as exactly64 lowercase hex; relational maximum64; ApplicationId max 400; ApplicationRevision positive; ApprovedAt/FactorVerifiedAt/ReplayUntil UTC seconds, FactorVerifiedAt <= ApprovedAt < ReplayUntil; AuditId required unique FK restrict. ScopedKeyHash generated as exactly64 lowercase hex, relational maximum64 and unique index; digest binds actor/action/application/request key and exact fields are compared on lookup to fail closed on collisions. |
| ApplicationGrantAudit | AuditId required PK/FK to SecurityAuditIntent; JobId required FK restrict; ApprovalId required FK restrict; JobRevision positive; AuthorizationDelta/TokenDelta nonnegative; cumulative counts nonnegative; exact bounded state/failure codes. Unique job/revision. |

Use ApplicationProjection.IdentifierLength (400) and FactorSchema.UserLength (450).
A composite text idempotency index would exceed SQL Server key width; index its canonical
SHA256 scope digest and verify exact fields rather than narrowing supported identifiers. Native records are selected by
exact application identity and remain manager-owned. Job-to-effective-approval association
is verified against the same job on every operation; no circular insert dependency is
required. Approval stores safe proof metadata, never token values, seeds or secret hashes.

Indexes support state/ObservedAt/Id polling and application/state incomplete-job checks.
Use provider dialect for portable constraints and ordinal text collation. Digest alphabet/exact length are generated by the SHA256 operation, not a database alphabet constraint; do not claim relational rejection of arbitrary shorter or nonhex digest inserts. Counters and
timestamps have database constraints as well as operation checks. Zero pending native rows
is a valid successful job; zero-change completion advances revision with atomic audit.

Transitions: queued → processing → succeeded; queued/processing → stopped; stopped → queued
only with a new explicit approval. Success is terminal. Restart does not reset counters,
revision, original scope or approval history. No lease/running flag authorizes work outside
the owned transaction. Completion does not change Enabled or any credential metadata.

Pending and stopped jobs block re-enable. Configuration edits/credential replacement may
continue under their existing separate permissions; they do not broaden job scope or
revive old grants. Target supported profile/native identity and disabled state are checked
every time. Original application revision records admission, not a permanent requirement
that would make harmless edits prevent recovery.
