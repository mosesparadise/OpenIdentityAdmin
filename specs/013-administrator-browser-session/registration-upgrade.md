## Implemented boundary

The one-shot Migrator selects `upgrade-administrator-browser-registration` explicitly. It requires redirected bounded UTF-8 public input, the current Platform schema and the registered relational provider. It uses the existing Platform-only operation path, clears provider logging, opens no listener, provisions no role and performs no schema migration. Neither a live issuer nor startup initialization calls the upgrade. [Operator instructions](../../docs/operations/administrator-registration-upgrade.md) record the required receipt-read privilege and intentional reconciliation procedure.

The production owner acquires governance before the protocol profile lock, then reads untracked current authority and freshly reloaded native application/scope descriptors. Input identifies the exact original callback, public JWK, canonical positive expected revision below Int64.MaxValue, operation UUID and bounded operator reference. The command derives the B3 variant internally; callers cannot submit an arbitrary target manifest. Exact B2 recognition rejects partial/extra metadata, native disabled markers and drift. The supported disabled shape is `AdministratorProtocolProfile.Enabled=false` with otherwise exact enabled native metadata. This is the existing profile disable boundary; it remains false through the upgrade. Unsupported native disabled markers are rejected unchanged, never repaired or re-enabled.

One owned transaction updates only the native application B3 delta, invalidates pending native request tokens, advances profile revision exactly once, preserves the nondecreasing observed-time watermark and enabled state, and writes one sanitized audit. Application/scope identities, scope manifest, callback/key and migration histories remain intact. The audit records event `administrator-browser-upgrade`, actor type `deployment-operator`, operator reference, fixed profile target, operation correlation, observed time and outcome `upgraded-to:<revision>`. The largest representable target fits the existing 32-character outcome column. No key, token, subject, private assertion or provider diagnostic enters the receipt/output.

Native `IOpenIddictTokenManager.RevokeAsync` receives the persisted application ID, valid status and private request-token type. Before and after bulk update, a bounded metadata-only scan enforces the existing 20,000 retained-token and 10,000 request-token ceilings, canonical request type/status, exact affected count and no remaining valid request. This rejects case variants whose SQL collation could otherwise make providers disagree. It preserves authorization-code, access/ID-token and other-application rows. OpenIddict's private request-token type can represent several cached request kinds; the exact old B2 registration has only PAR and no request caching/end-session capability, which is why this transition can use that type as its pending-PAR boundary.

Only the exact same original operation, operator and expected revision may reconcile an already committed exact B3 revision N+1. Exactly one matching audit must exist. Reconciliation returns unchanged and rolls back all lock-only updates; it does not revoke fresh B3 requests, create another audit or increment a revision. A different command, missing/duplicate/altered receipt, stale revision or structural drift fails unchanged. Commit acknowledgement loss is reported as failure; the command never automatically retries. An intentional later invocation can prove the committed outcome through the same exact receipt and state checks.

The original 10-second request, 5-second write and 5-second cleanup bounds remain unchanged. Time is sampled before the audit and again after reloading final metadata; backward movement beyond 30 seconds rejects the transaction. No provider-specific production SQL, new database schema, provider registration change or legacy allowance is introduced. Current B2 issuer composition deliberately remains B2 and rejects upgraded metadata; deployment activation must await the later explicit B3 composition and its acceptance.
