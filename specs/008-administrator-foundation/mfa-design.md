# Administrator MFA and restricted recovery — increment 2 design

Status: independently reviewed design for feature 008 T016; no account-journey implementation or runtime acceptance is claimed. The approved second implementation increment covers password plus TOTP and single-use restricted recovery. Passkeys remain M05; Admin BFF/API and production documentation activation remain M02-B–D. This design does not add emergency reset, email recovery, remembered devices or certification claims.

## Composition and project boundaries

Preserve the approved grouped projects, thin Programs, Composition extensions and explicit Features/Setup registration/mapping. Add only the necessary Enrollment, Mfa, Recovery and Security journeys beneath AuthServer/Features/Accounts, each with Setup.cs. Keep Razor handlers small; handlers validate the HTTP boundary and invoke cohesive feature services. Shared account browser protection belongs under Accounts/Shared, not a dependency on private pilot handlers. Core/Features/Identity owns state/policy contracts; Infrastructure/Features/Identity owns protected native store adapters and persistence. Use the existing two migration projects and dedicated Administrator Aspire tests. No new production host or generic repository is proposed.

Current AddAccounts/MapRazorPages is activated through the Development pilot. Refactor shared account configuration so explicit `Identity:AdministratorAccounts:Enabled` registration can activate administrator pages with valid issuer protection independently of the pilot. Default is false; malformed options or enabled-without-protection fail startup. Enabling administrator accounts must not enable pilot provisioning, protocol clients or management endpoints. Administrator-only composition explicitly installs request deadlines, database command/lock bounds, security headers, safe diagnostics and rate limits without relying on AddPilotProtection. Explicit Razor conventions exclude pilot pages when the pilot is off and administrator pages when their feature is off; merely mapping every compiled Razor page is insufficient. Test all four feature combinations. Preserve the pilot's named scheme/cookie and role-bearing/MFA-user rejection.

Administrator authentication uses its own named full-session scheme and `__Host-identity-administrator` cookie. Restricted interactions use opaque browser correlation cookies, not an authenticated administrator principal. No default/fallback scheme accepts either a pilot ticket or a restricted interaction as administrator proof. Until M02-B–D, the full administrator session is usable only for its own account security/status/logout journeys; it authorizes no management API, BFF, documentation or OAuth client. No new token grant is introduced.

## States and eligibility

Enrollment states are Pending, Active and RecoveryRequired; suspension is an orthogonal flag, not a competing enrollment state. Preserve the permanent bootstrap receipt. A separate suspension marker records deliberate prohibition of enrollment/recovery, distinct from bootstrap's intentional `IsEnabled=false`. Suspension invalidates interactions and sessions and cannot be undone by successful credentials. The future governed mutation service must own suspension/unsuspension; this increment exposes no operator bypass.

Initial enrollment requires the exact receipt user, consistent consumed bootstrap/governance state, Pending enrollment, expected revision, no suspension, no existing active factor, native lockout eligibility and the bootstrap-disabled account. Never temporarily enable the account to pass SignInManager checks. Ordinary disabled, deleted, unowned or active users cannot use this exception. Password success creates only an initial-enrollment interaction. The account becomes enabled/Active only in the successful factor-proof transaction. Existing Pending rows migrate without granting authentication authority; inconsistent rows fail closed.

Active login requires enabled, unsuspended, unlocked account and Active enrollment with a current protected factor. RecoveryRequired admits only the defined recovery/replacement paths, never normal login. A disabled account other than the narrow initial bootstrap state cannot authenticate or recover. Every transition rereads authoritative state under its transaction lock; a cached principal or role name is insufficient.

## Explicit initial policy

| Policy | Initial value and ownership |
| --- | --- |
| Restricted interaction expiry | Five minutes from creation; absolute, non-sliding; each next stage requires its authorized predecessor |
| Interaction attempts | Five submissions; a failed fifth submission exhausts and consumes it; a correct fifth submission may succeed if account budgets remain eligible, without refreshing its expiry |
| Account failed-proof budget | Five failed password/factor/recovery attempts across nodes and interactions, followed by five-minute native account lockout |
| Recent complete MFA | Five minutes; measured from actual factor verification, bounded by password verification freshness |
| Sensitive self-service changes | Fresh password and previously unused TOTP, each within five minutes, bound to one requested action |
| Administrator session | Thirty-minute idle and eight-hour absolute maximum, as approved; no remembered-device bypass |
| TOTP input | Exactly six ASCII digits, without trimming, Unicode-digit acceptance or integer coercion |
| TOTP verification | Pinned native Identity authenticator provider; five 30-second counters; no claim of a matched counter |
| Replay retention | Five minutes per factor generation; never evict live entries to admit another proof |
| Clock rollback bound | Thirty seconds against a durable monotonic observation watermark; larger rollback denies and retains replay evidence |
| Recovery codes | Ten distinct codes, each 128 CSPRNG bits; display as 32 uppercase hexadecimal digits with optional fixed grouping on the page |
| Request bounds | Existing 16 KiB body, bounded form count/values and ten-second request deadline; no request body or credential logging |

Represent these policies with feature-owned names and documented options only where deployment adjustment is intended. Security ceilings cannot be increased merely by editing appsettings. Input display grouping may be removed only at explicit ASCII hyphen positions; persisted verifier input has one canonical representation. Unknown/extra form fields and duplicate security-critical values are rejected. Test exact inclusive/exclusive boundaries independently of product constants.

Correct password alone never resets the factor failure budget. Use native UserManager password verification and checked native lockout operations under serialization; do not use a password-only sign-in helper that resets failures or issues a cookie. The user authentication row owns the combined consecutive-failure count and LockoutUntil; native LockoutEnd is set through checked UserManager.SetLockoutEndDateAsync at the threshold in the same transaction. Administrator failed attempts increment only this product counter; they do not call AccessFailedAsync or treat native AccessFailedCount as a second authoritative counter. Clear obsolete native AccessFailedCount through its checked manager operation only on complete success or legitimate lockout expiry. Before LockoutUntil, deny even correct credentials. At or after the exact expiry, the first serialized attempt opens a fresh zero-count budget and clears expired native lockout; it does not create a session or revive an exhausted interaction. Apart from this explicit time-based reopening, reset the combined budget only after the entire required ceremony succeeds. Native lockout that independently remains in the future still denies; missing or invalid product budget state denies without automatic repair. Native counter differences caused by prior framework use are not evidence of MFA success and cannot reset the product budget. Unknown/ineligible users take bounded dummy password work and return the same generic denial. Browser and host admission budgets apply before expensive work; account budgets are durable and cannot be reset by clearing cookies.

## Interaction and browser contract

Routes are same-origin Razor pages beneath `/account/administrator`: enrollment, login, mfa, recovery, security and logout. GET renders forms/status only; POST owns state-changing actions. Use native Razor antiforgery for every POST, TLS, secure HttpOnly host-only correlation cookies, SameSite=Lax, no-store/no-referrer/nosniff and the existing strict nonce-based CSP. Do not use unvalidated return URLs. Successful journeys end at the fixed account security/status page until real protocol continuation is implemented in its own milestone.

Interaction IDs and correlation secrets each use 256 CSPRNG bits. IDs are opaque locators, not credentials; store only a digest of the correlation secret. Bind the durable interaction to user, purpose, enrollment/factor generation, current security stamp, initial password verification time, browser digest, creation/expiry, attempt count and terminal state. Allocate/rotate correlation secrets on each authorized transition. A recovery or enrollment interaction cannot be swapped into a login or sensitive-action purpose. CSRF/binding failures do not consume a different browser's valid interaction. Bound identifier shape before database access; do not log raw IDs, cookies or query values.

An initial anonymous form admission has no account authority. Enforce at most eight live interactions per browser budget using a shared database lock, plus a host limiter of 600 requests per minute and 16 concurrent requests, no queue, for the account surface. Reuse the tested admission mechanism only after extracting a genuinely shared policy-independent primitive; do not copy the pilot's large fixture/handler code. Cap per-account live interactions at eight under the account lock. Exhausted capacity denies allocation without evicting another interaction. Expiry/consumption releases capacity; test simultaneous eighth/ninth admission on separate nodes. Edge/global deployment rate protection remains an operational requirement, not a claim that browser cookies identify an attacker.

## Native managers and protected stores

Use native UserManager/Identity token-provider orchestration, not manual password hashes or a parallel account database. Implement the native authenticator/recovery store interfaces using the existing scoped PlatformDbContext. Authenticator reads/writes must use the verified shared AuthServer Data Protection ring; default native plaintext seed/token storage is prohibited. Register that adapter deliberately for AuthServer. Migrator's password-only bootstrap path must still resolve without issuer DP, must not create an ephemeral ring, and must reject unsupported factor operations rather than silently storing plaintext.

Purpose strings bind product feature, format version, canonical issuer, user ID, material kind and generation. Use distinct purposes for staged seeds, active seeds and accepted-code replay evidence. A staged seed also binds its interaction. Missing keys, corrupt ciphertext, cross-user/generation substitution or failed unprotect deny safely; never generate a replacement automatically. Retain historical ring keys/wrapping decryptors for every still-live durable factor, not merely cookie lifetime. Protect backup/key access as described in the issuer runbook; database-only disclosure must not reveal seeds.

Override the native UserManager protected `CreateTwoFactorRecoveryCode` generation hook with 128 random bits; keep native generation/redeem orchestration. The recovery store keeps only a one-way SHA-256 verifier over an unambiguous, length-prefixed domain/user/generation/canonical-code encoding, plus redemption state. High-entropy codes make offline guessing infeasible; no reversible code collection or raw native joined token field is permitted. Require exactly ten distinct generated values or roll back. Check every IdentityResult, propagate cancellation and retain the manager/store transaction; no blanket retries.

Pinned provider validation returns a Boolean and uses DateTimeOffset.UtcNow internally. A TimeProvider injected into application policy does not control that clock. Native verification tests generate independent codes around the real observed clock and explicitly handle boundary observations; application expiry/watermark tests use their own deterministic clock seam. Native test OTP generation uses an independent RFC6238 oracle with published-vector controls; negative outside-window values must differ from every value in the accepted window. Record safe before/after counter relations to identify a crossed boundary; never retry a failed authentication operation until it passes. Do not replace the native algorithm or use reflection to access private counter helpers.

## Replay and transaction ordering

Serialize every factor decision through a persistent per-user authentication row using a real UPDATE lock on either provider. Its generation, revision, failure count and observation watermark survive restart. Use one lock order for all paths: governance singleton (when needed), the installation admission singleton (when allocating), browser-budget rows in ordinal ID order, user-authentication rows in ordinal user-ID order, then interaction/factor/recovery/session rows in ordinal key order. Enrollment activation, recovery entry and replacement require governance. Admission, completion, invalidation and cleanup use this same order for every row they touch; a path must never acquire an earlier lock after a later one. Discover required identifiers before acquiring locks, then revalidate every relationship after acquisition. Capacity is derived from current interaction state under the budget lock, not released through a reverse-order callback. Bulk invalidation sets user generation/stamp and terminal state without subsequently taking another browser lock; future admissions recompute live counts. Cleanup uses bounded ordered batches and skips a contested batch instead of changing order. Ordinary login need not hold installation-wide governance while hashing. After acquiring locks, reload tracked native state to avoid stale manager entities.

For each factor proof, recheck current state/binding/expiry/budgets, compare the submitted ASCII bytes in constant time with the bounded recently accepted DP-protected code entries for that factor generation, then invoke native verification. After native verification, sample UTC again, recheck the clock fence, interaction expiry and freshness, and timestamp the replay reservation from that post-verification observation; production policy time uses TimeProvider.System on the same UTC basis as the native provider. On success reserve the code in the same transaction as interaction consumption, session/state mutation and successful audit intent. Enrollment proof, login, step-up and replacement of an existing factor all share the ledger. Two interactions on two nodes cannot accept the same code. A coincidentally repeated numerical code within retention is conservatively rejected; the user waits for a new code.

Retain at most 64 live accepted-code entries per factor generation; capacity exhaustion fails closed rather than evicting evidence. Prune only when the persisted timestamp plus five minutes has passed and the clock fence is healthy. Update the durable watermark to max(previous, observed UTC). A request more than thirty seconds behind it is denied without pruning. A forward jump followed by rollback remains fenced by persisted state, including after restart; do not clear the watermark to repair an installation. Small cross-node skew is covered by the conservative five-minute retention, exceeding the native window plus the allowed skew. Operations must monitor UTC synchronization.

Successful mutations and sanitized success audit commit before issuing a cookie, redirect or secret-bearing response. Audit failure, manager failure, cancellation or precommit process death rolls back the entire transition. Failed credential attempts and their sanitized denial audit also commit together; dependency/audit failure denies without fallback. Use fixed safe external errors and correlation-only operational diagnostics. Lost commit responses never trigger automatic sensitive-operation retry: the consumed interaction stays consumed, and the user starts the documented fresh journey.

## Ceremonies and loss handling

1. **Initial enrollment:** validate fresh password through the narrow Pending eligibility path, create a bound five-minute interaction and stage a newly manager-generated authenticator key protected for that interaction. Display the manual setup key only on that restricted no-store page; no third-party QR service. Manual entry is the first increment's supported enrollment method; a QR enhancement requires its own reviewed dependency/encoding and secret-safe tests. Confirm one native-valid unused TOTP. Allocate the destination factor generation when staging, bind the interaction and proof to it, then atomically install that exact generation and protected seed, reserve that code against the same generation, enable native TwoFactorEnabled, enable the account, mark Active, rotate the security stamp and recovery generation, consume the interaction, generate ten recovery verifiers, create the eligible session and audit. Activation must not increment the factor generation again or orphan the accepted proof. Display recovery codes once after commit. If activation's response is lost, the proven authenticator remains usable; a fresh password/TOTP login can explicitly regenerate codes. Reposting never redisplays or silently regenerates them.
2. **Ordinary login:** password success grants only an MFA interaction. Native-valid unused TOTP, current eligibility and remaining budgets are all required before recording password/factor verification times and creating a new session. Replace only the browser's prior session where appropriate; no session fixation or raw Identity principal is accepted. The session cookie is issued after commit, is nonpersistent, and cannot refresh the absolute deadline.
3. **Recovery entry:** require a fresh password and one unused recovery code for the current recovery generation. Atomically redeem exactly that code, revoke existing administrator sessions and interactions, rotate the security stamp, disable use of the old factor, set RecoveryRequired and create a fresh bound replacement interaction with a sanitized audit. Issue no full session. Remaining unused codes stay usable only for a fresh password-plus-code recovery entry if the current interaction expires or is lost. Never resume replacement with password alone. The old authenticator does not resume normal login while RecoveryRequired.
4. **Recovery completion:** within the authorized interaction, stage a new key and require its native-valid unused TOTP, plus password proof no older than five minutes. Stage against a newly allocated destination generation and reserve its confirmation code against that same generation. Atomically make that destination active, retain its newly accepted replay entry, invalidate only obsolete generations of recovery verifiers and factor/replay/proof material, create ten new recovery verifiers, mark Active, rotate the security stamp, consume the interaction and audit. A new eligible session may then be issued using the actually verified password and new factor times. Old cookies/codes/factors are denied on either node. Lost completion response follows the same fresh-password/new-TOTP code-regeneration route as enrollment.
5. **Voluntary factor replacement or recovery-code regeneration:** require current full session, fresh password and an unused current TOTP, bound to exactly one action and consumed atomically. Replacement allocates a destination generation, stages a new factor and proves it before replacing the old active factor; its proof reservation follows that destination into Active, while the old-factor step-up reservation stays associated with the old generation; abandoning staging must not destroy a valid active factor. Regeneration invalidates all old codes, rotates relevant security state and revokes other sessions; return a replacement current session only after commit. Replays cannot regenerate twice. There is no factor-removal/password-only mode.
6. **Logout:** a CSRF-protected POST revokes the current stored administrator session, audits and clears its cookie; GET only presents confirmation. It does not claim unimplemented OpenID Connect logout or BFF logout acceptance.

Staging does not call a native reset operation against the active key. Generate the staged key through the native manager and protect it in product staging storage. A scoped, internally authorized factor-selection context lets the native provider retrieve only that interaction's staged key during confirmation; it is never selected from a caller-supplied user/generation alone, never static/AsyncLocal global state, and never visible to ordinary login. A narrow derived UserManager installation method accepts only the internal verified staging result, calls its protected IUserAuthenticatorKeyStore adapter to set that already-proven seed, then performs checked native user update/TwoFactorEnabled/security-stamp operations in the same outer transaction. There is no public native setter for an arbitrary staged seed: do not substitute SetAuthenticationTokenAsync or ResetAuthenticatorKeyAsync, which could write the wrong storage or generate a different key. The internal result is account/interaction/destination-generation-bound and cannot be constructed from request fields. Test actual native-manager dispatch and scope disposal, not only a fake verifier.

**All-factor loss:** a user lacking both a working authenticator and an unused recovery code has no recovery route in this increment. Keep bootstrap consumed and deny safely. An expired replacement interaction plus no remaining code is the same blocked state. Loss of the bootstrap password before activation is also blocked. Document the operational incident without adding database edits, email/support reset, disabling MFA, alternate operator credentials or restoration of spent codes. Future emergency recovery requires a separate concrete design and explicit approval before implementation. This limitation is a release-readiness dependency, not a claim that full R1 account recovery is complete.

## Authoritative sessions

Store opaque session ID, user ID, security stamp, factor/enrollment generation, password verification time, factor verification time, created/last-activity/absolute-expiry and revocation state. Persist actual methods `pwd` and `otp`; never encode successful `otp` for recovery-code entry. A session references the committed generation; cookie claims carry only the minimal identifiers needed to resolve it. Never place stamps, factors, recovery codes or privilege catalogues in browser-readable data or token claims.

On every protected account request, read current user/enrollment/session/generation/stamp, the authoritative authentication-state budget/LockoutUntil and native lockout state. Require native LockoutEnabled=true; missing/inconsistent product budget state or either unexpired lockout denies even when a native helper alone would ignore LockoutEnd. Deny on missing/deleted/disabled/suspended/locked/recovery-required state, expiry, revocation, mismatch or unavailable database; no periodic-stamp grace or stale cache fallback. Sliding idle activity is persisted with a bounded atomic update, cannot extend the eight-hour deadline and never updates authentication times. Sensitive action freshness is evaluated again at mutation commit. Current permission/governance policies and the five-second API/BFF revocation bound remain increment 3/M02-D, not claims of this account-only session.

Recovery/replacement rotates account security state and revokes all previous administrator sessions/interactions in the platform transaction. Existing pilot eligibility already rejects role-bearing/MFA identities; preserve that rule and explicitly invalidate any legacy local sessions for the same user. There are no administrator grants in this increment. When M02-B introduces them it must wire this same invalidation boundary into authorization/refresh/token/current-state checks before accepting administrator tokens.

## Persistence additions and operations

Extend enrollment with explicit suspension and factor/recovery generation. Add user authentication state (lock/revision/failure/watermark), restricted interactions (purpose/binding/expiry/attempt/state/staged ciphertext), protected active factor, accepted-code replay entries, one-way recovery verifiers with single-use state, administrator sessions and browser admission budgets. Use bounded strings, positive generations/nonnegative revisions, ordinal collation where needed, uniqueness per generation/verifier, expiry/user indexes and no cascade that erases successful audits or reopens bootstrap. Recovery verifier comparisons and mutable row claims must have provider-independent single-winner semantics.

Migrations are additive on both providers, preserve existing pilot/account data and permanently consumed bootstrap, and update SchemaCatalog/readiness together. Existing data is not promoted to Active or treated as MFA proof. Runtime uses DML credentials; fault injection/migrations alone use elevated test credentials. An AuthServer-hosted cleanup service registered explicitly through Accounts/Setup owns metadata cleanup; no new Worker scope or protection dependency is introduced. Every sixty seconds it attempts at most one hundred rows per category under a five-second cancellation deadline and the common lock order; contention rolls back that batch and waits for the next scheduled pass. Multiple hosts coordinate through database locks, not in-memory leadership. Expired/consumed interactions, unused browser budgets and revoked/expired sessions become eligible for deletion immediately when terminal and unreferenced; healthy-service physical deletion has a twenty-four-hour target, not a guarantee during an outage. Replay rows retain at least their required five minutes and clock-fence safety; retired factor/verifier/staging ciphertext is removed transactionally at replacement or after its interaction expiry. Limit each user to eight unexpired administrator sessions (new ninth login fails without evicting another session), eight live interactions and sixty-four retained replay entries per factor generation (prune eligible entries before deciding capacity; never evict live evidence). Cap retained sessions at thirty-two per user and ten thousand installation-wide, counting expired/revoked rows until physically deleted. Allocation is additionally capped installation-wide at ten thousand retained interactions and ten thousand retained browser-budget rows, including expired/consumed/unpruned rows, through a dedicated admission singleton, acquired before browser rows and after governance when used. Create a new budget only within the same admitted interaction transaction; anonymous GET cannot persist an uncounted budget. Count/claim retained session capacity under that same singleton when creating a session. Cleanup takes it before physically deleting any counted rows, preventing stale released capacity. Counts include replacement interactions; transition within the same persisted interaction slot with a fresh public identifier and browser secret, irrevocably invalidating its predecessor binding. Distinguish that slot key from its replaceable public identifier. No independent expiry event decrements retained capacity. At the retained ceiling deny new allocation with a generic retry-later response while preserving existing valid sessions and nonallocating interaction operations; if session allocation lacks capacity, deny before consuming factor proof or mutating authority and retain the bound interaction until its original expiry; never delete live authority to free space. Cleanup/pruning uses metadata, not decrypted secrets; it never clears a live generation/watermark. If cleanup is unavailable, expiry still denies credentials, caps still deny new allocation, and backlog telemetry reports degradation. Retained successful audit evidence is independent of this short-lived state. Cleanup prunes only after safety checks; it never deletes audit/receipt or resets generations/watermarks. Factor/recovery material retirement remains transactional with replacement. Missing keys are an operator incident, not an automatic reset.

Expose only low-cardinality counts/durations/outcomes for admission, verification, replay rejection, lockout, audit/database/protection failure and active cleanup backlog. Never emit usernames, submitted codes, keys, cookies or raw exceptions. Keep secret-bearing pages out of Playwright screenshots/videos/traces, accessibility HTML dumps and network payload capture, including failure hooks. Sanitized tests assert layout/accessibility without retaining secret text; fixed labels and result classifications suffice for diagnostics. Synthetic data does not authorize routinely retaining live test credentials.
