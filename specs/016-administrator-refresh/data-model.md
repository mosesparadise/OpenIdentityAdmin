# Refresh data model and ordering

Planned logical model, not a migration or implementation claim. T003/T005 will bind names/columns/constraints to actual provider models. Use existing portable integer revisions and short database ownership; no SQL-Server-only concurrency semantics.

## Sessions-owned state

| Entity | Fields and invariants |
| --- | --- |
| Credential generation | One row per existing ticket digest (64 uppercase hex characters); revision is positive Int64 and checked for overflow. Protected envelope contains access/refresh credential values, native validated identity context, issuer/client/subject/source/authorization binding, access expiry, immutable original refresh/source/local absolute deadlines and original idle duration. All lifetime values use UTC ticks and strict expiry at equality. No cleartext token or raw handle column. |
| Refresh operation | One active operation per ticket; 32 random bytes encoded base64url as opaque operation ID, never authority by itself. Expected credential/ticket revisions, browser digest/generation, creation and immutable deadline, state `Reserved`, `Dispatched`, `Committed` or `Terminal`. Each transition checks the exact original binding. An expired operation cannot become a new dispatch owner. |
| Cleanup intent | One preallocated cleanup slot per admitted credential family, initially `Reserved` and changed to `Pending` by its terminal transition, deduplicated under local ownership; protected original target and authenticated family binding, fixed reason/outcome, created/deadline, revision and attempt metadata. No token in logs, unconstrained exception text or user-supplied endpoint. Confirmation records only fixed outcome plus opaque correlation. |

B1 and B3 protected binding/lifetime validations remain mandatory; a plaintext digest or operation row never establishes identity. Credential envelope uses a distinct versioned purpose and authenticates all binding/deadline/generation fields. Reprotect on mutation, retain old decryptors until expiry/invalidation, fail closed on tamper/missing keys. Maximum plaintext envelope 64KiB and maximum protected envelope 128KiB; test at/beyond bounds and serialized overhead. Do not enlarge existing B1 limits to accommodate credentials: keep the separate envelope.

Existing Sessions budget owns a maximum 10,000 retained credential rows, 10,000 retained operation rows and 10,000 retained cleanup intents, with at most one active operation and one pending cleanup per credential row. Terminal/expired rows count until deletion; reserve capacity atomically, deny at cap and never evict live rows. These are implementation bounds, not a production sizing claim. Before the native initial code exchange can issue any refresh family, reserve its eventual credential/cleanup capacity under the durable browser login attempt. This includes replacement, callback-failure and orphan paths. The later successful callback atomically binds that existing reservation to its authenticated family and ticket; it does not allocate cleanup capacity after issuance. T003 must prove an authenticated cleanup target recoverable from the original fixed-client login/exchange binding even if the token response is entirely lost, with the protected pre-send reservation retained until its possible family expires or is confirmed denied. A fabricated/unbound family selector or reliance on receiving the new token is insufficient. No refresh-enabled initial exchange is allowed before this prerequisite is proved. If no slot is available, send no new refresh-enabled code exchange; retain existing local sign-in behavior only through the separate code-only profile, never silently downgrade a refresh-enabled response. Logout/terminal invalidation updates its already-reserved slot and needs no new quota allocation. Keep the slot reserved while any associated credential or unresolved cleanup/tombstone remains retained; deleting a credential row alone cannot free it. Both-provider quota-full logout, failed admission rollback and concurrent admission/replacement tests must prove this guarantee. Existing browser/ticket and native token budgets remain additional constraints.

## State machine

1. Native callback validates the exact refresh-enabled fixed profile and response, then atomically creates B1 ticket, protected credential generation and browser association plus audit, and binds the already reserved cleanup slot in Sessions. Failure installs none. Existing code-only callback continues without a credential row.
2. A protected demand reads canonical ticket/credential/generation, validates all deadlines and authentication. If access is still valid, return unchanged local status; do not touch idle/source activity. If expired, reserve the exact predecessor and operation with audit in a short transaction.
3. Immediately before HTTP, commit `Reserved → Dispatched` against current ticket/revision/browser generation and immutable deadline. The native send requires that in-memory receipt and remaining deadline. No lock spans HTTP. A crash between durable dispatch and send sacrifices availability: it is uncertain, never safe to retry.
4. Issuer independently serializes native refresh validation and durably consumes the predecessor in an early owned epoch. Consumption commits before later issuance and survives its rejection/rollback. A request-local owned receipt permits only that native operation to continue; it cannot bypass later authorization denial. The separate final issuance epoch rechecks current authority/time/family state under the common invalidation ordering and atomically commits rotation, native manager state/quota changes and audit. A replay/cleanup denial committing first prevents successor issuance; issuance committing first can complete, while subsequent family denial invalidates linked credentials. T003 proves the exact child/parent transaction and manager boundaries; no single rollback may restore a spent credential. Successful issuance commits before admitting the protocol response.
5. Validate native response and original bindings. In a short Sessions transaction, require the same dispatched operation, live original ticket/browser generation, current revision and every deadline. Atomically replace protected credentials, renew B1 under its original policy, commit audit and mark operation committed. Do not restore a revoked row or copy a new absolute cap. After successful scope disposal and final deadline checks, publication may refresh the same session/generation cookies only to the new effective idle deadline within all original caps; proof identity/creation/absolute expiry stay unchanged. Late old cookies cannot defeat durable generation/revocation, and no cookie is renewed on a no-op or contender read.
6. A contender never sends the predecessor. It may perform a bounded read after the winner finishes and use the independently authenticated committed successor; otherwise return busy. No polling loop extends the request deadline or renews idle time.
7. Before-dispatch cancellation can terminate the reservation without spending a credential, only if durable state proves `Reserved`. Once dispatch may have happened, any unknown outcome marks capability terminal/local ticket unusable and activates its preallocated cleanup intent. Failure to persist terminal state leaves durable `Dispatched` unusable to all request paths; later reconciliation can only deny/cleanup, never dispatch again.
8. Local logout/replacement atomically advances browser generation, revokes ticket/credential capability and activates its preallocated cleanup intent. A response arriving later fails the final fence. Issuer revocation and local completion are separate. If refresh committed first, logout targets the current family; if logout committed first, a late owner cannot install its successor and the intent must invalidate that same family.

A paused owner that resumes after timeout must recheck its immutable deadline before native send and publication. It cannot reclaim an operation. An already admitted network request may reach the issuer after local logout; local publication remains denied, and issuer family revocation ordering must deny all issuance following its commit. No distributed instantaneous-cancellation claim.

## Issuer-owned state

Use native token/authorization IDs, managers and their existing Platform ownership. Add only the minimal product binding/deny metadata needed by characterized native integration; no second token store. Exact subject/source/client/original deadline is protected in native refresh principal and cross-checked against current stored authority. No permission snapshot or new password/factor timestamp.

The native refresh authorization must be distinct per authenticated family. Reuse/cleanup invalidation must not affect unrelated sessions or pilot grants. Initial fixed-profile registration explicitly adds refresh/offline and native revocation eligibility; old-profile upgrades must reject unexpected drift and use managers. Initial token expiry is the minimum of the source deadline, original local/refresh eight-hour cap and shorter policy. Every successor preserves that original maximum even if a new token ID is generated.

Continuing refresh uses current source idle/absolute state, security stamp, enrollment/factor generations and administrator permission eligibility without requiring password/factor age under300s. Successful committed issuer refresh can advance source activity monotonically within existing policy; source absolute expiry/authentication times remain immutable. Native manager replay/authorization checks cannot be replaced with cached plaintext metadata.

## Cleanup and recovery

Cleanup batches are at most100 per owner/invocation, preserving existing quotas. Do not delete dispatched/replay tombstones, predecessor-family evidence or pending cleanup while any corresponding credential/family could remain usable. Retain through original maximum lifetime plus native retention, then delete only after current eligibility/dependency recheck. Ended local metadata uses existing30-day retention where applicable; audit retention is independent. Expired pending cleanup records retain a finite unresolved outcome rather than fabricate confirmation. Never retain raw credentials past the bounded cleanup need; reconcile expiry using the known original cap and then erase their protected values.

No generic background refresh. An explicitly invoked bounded cleanup worker/reconciler may attempt idempotent family revocation with fresh proof and exact durable target; at most one concurrent attempt per intent, ten-second attempt deadline, no in-attempt HTTP retry. Scheduling must be explicit, bounded and tested in T017/T020, and disabled until that acceptance. Restored snapshots require issuer family/session invalidation plus Sessions invalidation before reopening; the runbook must account for two stores and retained keys.
