# Administrator refresh contracts

Planned contracts; no routes or grants are added by this packet. Protocol remains native/unversioned. Local browser-session endpoints follow existing `/bff/session` metadata conventions, not management API resource versioning.

## Browser boundary

| Request | Planned behavior |
| --- | --- |
| `GET /bff/session` | Existing read-only local status, unchanged. Never renew, dispatch refresh, set renewal cookies or represent API permission. |
| `POST /bff/session/refresh` | Explicit same-origin, authenticated-generation, antiforgery-protected demand. Accept only the native antiforgery form field and no query/credential/scope/target fields; use existing bounded form/origin policy. No browser bearer authentication. |
| Successful demand | `200`, existing minimal authenticated/subject/effective-expiry shape, `Cache-Control: no-store`. No OAuth values, handles, grant identifiers or claim/permission snapshots. Live access means unchanged status; an expired access credential permits one owned refresh. |
| Missing/ended local session | `401`, no HTML challenge or implicit sign-in. |
| Invalid origin/CSRF/framing | `400`, no authority change; preserve the existing browser policy's finite rejection behavior. |
| Another refresh operation owns the generation | `409`, no credential send, no automatic browser retry. Caller may later read status; a new explicit demand may only consume an authenticated committed successor. |
| Dependency/deadline/ambiguous result | `503` where a response can safely be sent, otherwise abort. No success body or staged cookies after failed cleanup/disposal. Uncertain dispatched state is unusable. |

Add operation metadata, cookie+antiforgery requirements, error/header shapes and generated-client/compatibility tests through the existing contract pipeline. No browser-facing OAuth endpoint or arbitrary HTTP proxy is created. Status is not enough to distinguish a live local ticket from current issuer authority; the refresh path must apply its own checks. Return generic denial for ineligible state without leaking account/client policy details.

Preserve all native secure host cookie attributes and B3 generation binding. After successful owned refresh installation and scope disposal, reissue the same opaque session handle and same protected generation proof with cookie lifetime capped to the minimum of the new idle deadline and all immutable local/source/proof/absolute deadlines. Do not change identity, generation, proof creation/expiry or original absolute lifetime. Recheck deadlines immediately before publication. No renewal cookies on live-access/no-op, contender successor reads, GET, failure or uncertainty. Logout/replacement still invalidates the generation: a delayed old cookie may not authenticate after the winning durable transition, and cannot restore a session. Browser tests must sustain active use beyond the initial thirty-minute cookie interval, then prove idle/absolute expiry and lost/late-cookie behavior. Preserve trusted forwarded-host/scheme handling; strip or reject browser Authorization/identity headers before they could affect native requests. Never propagate browser-supplied destinations, bearer tokens or cookies to issuer backchannels. Referrer policy, CSP and no-store controls stay intact.

## Native client and issuer

- Add a versioned refresh-enabled fixed administrator profile, leaving code-only profiles exact. Request `openid identity.admin offline_access` only on that opt-in flow; native permission/consent policy must actually grant it. Profile upgrade is manager-backed, rejects unexpected registration drift and invalidates incompatible pending requests; no silent widening of stored old grants.
- `/connect/token` accepts the native refresh grant only for the fixed permitted client, native `private_key_jwt` proof with existing replay protections, and a server-held refresh token. No cookie authentication substitutes for client proof. Keep request body16KiB, at most16 form values, keys128/value8KiB, ten-second total and five-second authority suboperation bounds. These bounds must accommodate actual native tokens or block integration pending a reviewed evidence-based change.
- Native validation supplies issuer/type/presenter/authorization/expiry and protocol errors. Product refresh proof supplies current user/session/factor/generation/client/admin eligibility and current scope/resource mapping. Rebuild minimal released claims; preserve native bindings, `auth_time`, AMR and immutable deadlines. No API-authority snapshot.
- BFF omits refresh `scope` to retain its existing approved grant. Native negative/contract tests cover permitted explicit narrowing and reject any expansion. Because the fixed application needs `identity.admin`, the BFF cannot install a response missing that required scope; it terminates local capability. Narrowing never creates another audience. Claim-release rules remain explicit even when there are no mutable public profile claims to emit.
- Initial proof age remains strictly under300s for new explicit sign-in; refresh current-state proof does not rewrite or require a new ceremony. Privileged management action freshness stays in M02-D/owning features.
- Invalid/expired/reused/wrong-client refresh yields native `invalid_grant` as appropriate; malformed input and invalid client retain native errors. Authority unavailable never yields success; record exact native safe error/status in T003. No cookie redirect or management ProblemDetails wraps OAuth errors.
- Native refresh output must contain a new refresh credential, bounded access credential/expiry and original binding. Validate any returned identity token natively; absence must follow the characterized native refresh contract, never fabricated identity. Reject incomplete, substituted, unexpectedly widened or oversized responses before installing state. Existing validated canonical identity can only be retained against proven unchanged bindings.
- Preserve request/deadline ownership through native-created child scopes, assertions and backchannel serialization; exactly one send after durable dispatch. No retry on network failure, protocol rejection, cancellation, disposal or lost response. Metadata GET behavior is separate and bounded by the same remaining operation budget.

## Replay, revocation and logout

Issuer serialization covers both successful refresh and adversarial concurrent reuse. Native redeemed-token validation alone is insufficient: verify manager return values and revoke the exact authorization plus linked credentials under owned durable policy. Swallowed native failures must poison acceptance; a rejected replay with failed revocation is not a completed family-compromise response.

Use native `/connect/revoke` with fixed-client authentication and a server-owned token target, extended by a narrowly reviewed product family-invalidation policy. The input never accepts an arbitrary browser authorization ID. T003 must prove native lookup of the authenticated retained predecessor even after rotation, exact caller/family ownership, disabled-issuance cleanup eligibility, lock order and replay/expiry handling. Unknown targets follow native nonenumerating behavior and must not revoke unrelated authority.

An ordinary RFC7009 empty200 conveys only native request completion. For the fixed first-party client, define and test a bounded authenticated response confirmation only after whole-authorization denial commits. Its final field/schema and native emission/validation hook belong to T003's reviewed inventory; dependent T017 cannot implement or claim confirmation before that contract is concrete. Do not treat a response extension as proof without TLS, fixed issuer/client binding and strict native request correlation. If confirmation is absent, lost or invalid, remote outcome remains unconfirmed even if a test later observes committed revocation.

Reserve credential/cleanup capacity before the initial native code exchange. T003 must prove authenticated family cleanup from the pre-send fixed-client login/exchange binding even when the initial response never arrives; no orphan path may depend on a returned refresh token to allocate or target cleanup. Local logout always commits local ticket/generation/credential denial first, activating the existing protected cleanup slot. Issuer cookie logout follows the existing independently protected flow; a return navigation never asserts either issuer cookie termination or family revocation. UI states must separately communicate local committed/unknown, refresh revocation confirmed/pending and issuer sign-out unverified. No message may retain the current “Refresh capability is not enabled” wording after enabling this feature.

A cleanup retry is a distinct idempotent attempt with new client proof and the same server-owned target; it is never a refresh retry. Prove duplicate successful family denial is safe without admitting unrelated token targets. Local session stays terminal throughout. Offline third-party access tokens may remain acceptable until expiry; M02-D alone will establish the platform API's online enforcement window.

## Internal interfaces

Use a feature-local coordinator (`Acquire`, `MarkDispatched`, `Install`, `Terminate`, `ReadCommitted`) with opaque receipts rather than caller-supplied state flags. Inputs are validated local binding/expected revisions and an original immutable deadline. Results expose finite outcomes; secret-bearing native results/envelopes must not acquire generated log-friendly `ToString` output. A separate `ReconcileRevocation` operation reads the protected cleanup target and cannot access Platform directly. Names are design vocabulary, not a requirement to introduce one interface per operation.
