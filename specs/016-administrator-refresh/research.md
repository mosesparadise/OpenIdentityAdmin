## Decisions and alternatives

1. **Continue the existing session, preserve fresh explicit sign-in.** Approved eight-hour refresh with current eligibility is incompatible with reusing initial five-minute ceremony-age admission unchanged. Share stable current-state checks, use a separate refresh proof, preserve `auth_time`/AMR and privileged-action freshness. Reauth on every refresh would defeat the approved continuing-session outcome.
2. **One protected credential generation per ticket.** Keep browser identity minimal and put the native validated credential tuple in a purpose-separated protected envelope in Sessions, committed with the ticket. Reject blanket token/property copying. Retain immutable issuer/client/subject/source/authorization/original-deadline binding and authenticated expiry metadata. Native validation, not manual JWT decoding, supplies trust.
3. **Short transactions around a durable dispatch boundary.** A portable revision/operation fence serializes Sessions writes; a committed `Dispatched` state precedes HTTP. Never hold a database lock over the network. No takeover after potential send: expired/crashed operations become terminal and require a fresh sign-in. A process-local semaphore or expiring lease with automatic redemption takeover cannot meet response-loss safety.
4. **Native issuer ownership with explicit replay policy.** Keep native token validation/cryptography/manager writes; add the minimal refresh-specific policy needed for fresh under-lock validation, early durable consumption that survives later issuance rollback, final under-lock authority/denial recheck and whole-authorization denial. Do not fork the native grant stack. The existing short profile/governance ownership may serialize more than one session initially; no throughput claim follows.
5. **No cross-store success fiction.** Issuer issuance commits before wire delivery; Sessions installs only a validated fenced response. Local logout commits denial and activates its preallocated protected cleanup intent together. Reserve initial family/cleanup capacity before code-exchange send, and prove cleanup remains targetable after total initial response loss. No distributed transaction is proposed. A sent request with uncertain result never falls back to prior access/refresh credentials.
6. **Separate revocation confirmation from logout navigation.** Extend the fixed-client native revocation boundary only after T003 proves target ownership, retained-predecessor lookup, authorization-wide invalidation and truthful confirmation. BFF supplies a protected server-owned token target, never browser-selected authorization IDs. Disabled issuance must not silently prevent authenticated, ownership-bound cleanup; prove the exact native policy. If native integration cannot satisfy this contract, stop that dependent path and publish a concrete correction rather than substitute token-only revocation.
7. **Bounded cleanup is an explicit idempotent operation.** Retain a cleanup intent for an unknown successor using authenticated family binding. A new cleanup attempt uses a fresh client assertion and the same durable target; it never resends refresh. No generic HTTP retries. Only an independently confirmed authorization denial completes the intent; unknown-token HTTP200 remains unconfirmed. Pending cleanup cannot revive local capability.
8. **Protected demand, no polling keepalive.** An explicit same-origin POST can request refresh; the later proxy calls the same internal coordinator. GET status stays read-only. No proactive timer or browser background polling renews session activity. Renew only when access has expired; a live access token yields unchanged status without activity writes. A contender may reread an already committed successor without causing another renewal.

No new product choice is unresolved after applying approved defaults and prior user answers. Native feasibility, exact response confirmation, event ordering and schema lock implementation are mandatory technical work with testable contracts, not assumptions of success.
