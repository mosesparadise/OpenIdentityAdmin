## Defect and design

`LoginInteractions.CreateAsync` counts only validated correlation cookies presented by that request. Two starts with the same seven-cookie snapshot can independently insert an eighth interaction, leaving nine. Serializing that snapshot-based count alone would still admit stale snapshots. First demonstrate the defect against the unchanged implementation.

Add a server-generated 256-bit opaque `__Host-pilot-budget` cookie and a digest-keyed `LoginBrowserBudget` in the platform schema. The budget credential identifies only an admission cohort; it never authenticates an account or replaces each interaction's independent correlation secret, antiforgery, original native request or completed-session binding. The cookie remains Secure, HttpOnly, Path=/, SameSite=Lax, no Domain. Check its persisted five-minute expiry after taking the lock, before any extension; expired credentials deny and expire the cookie. Refresh both server expiry and cookie lifetime only for a successful admission so the newest interaction does not outlive it. Last-admission metadata and expiry update in the same transaction as the interaction.

Each new interaction has a budget foreign key. Admission uses an explicit ReadCommitted transaction, first updating the budget row to acquire a database write lock, then counting all of that budget's unconsumed, unexpired interactions, regardless of the request's correlation-cookie snapshot. Admit only below eight; insert and commit under the same lock. Use provider-portable EF operations and a budget/live/expiry index. No process lock, global serialization, optimistic retry, mutable live counter or native-token SQL. Re-evaluate time and native expiry after acquiring the lock. Database and request cancellation bounds remain unchanged.

Completed interactions still occupy a slot until committed consumption or expiry. Consumption remains atomic with audit; uncommitted consumption never frees capacity. Admission may conservatively count the prior committed state or wait for the transaction, depending on provider locking. No decrement or compensation is needed. Failed/cancelled precommit allocation rolls back; emit no new budget/correlation cookie before commit. A committed allocation whose response is lost occupies its slot until consumed or expired; never reopen committed security state automatically.

Preserve the bounded nine-cookie inspection and stale/invalid correlation cleanup. Proven active cookies with no budget, a foreign budget or legacy unowned rows deny new allocation; never adopt or move them. Known budgets count hidden rows even when correlation cookies are absent. Malformed/unknown budget credentials deny without allocation and expire that invalid cookie so an explicit new attempt can recover. A clean cookie-free start creates a server-random budget. Independent browsers remain independent.

Browser identity is cookie continuity, not a physical-device guarantee: simultaneous entirely cookie-free starts or deliberately clearing all cookies cannot be identified as one browser without a different identity mechanism. The global request/rate limits remain separate. Do not add fingerprinting, IP identity or authentication privileges to solve this boundary.

## Persistence and upgrade

Add the model under Infrastructure `Features/Identity/Persistence`, feature-local admission code under AuthServer `Features/Accounts/Login`, both generated platform migrations/snapshots and SchemaCatalog entries. Budget ownership is nullable only for pre-migration interactions; those existing flows may still complete/consume with their original proofs, while further allocation carrying live unowned flows fails safely until those flows finish or expire. Stop the Development pilot, migrate and replace all hosts; no mixed-version admission guarantee. Preserve existing interaction tombstones and native request uniqueness. Budget retention/cleanup remains part of the existing future retention work; do not introduce an unreviewed pruning job.
