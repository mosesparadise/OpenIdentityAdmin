# Research and decisions

- **Validation**: Approved architecture (`03-protocol-security.md`, token-format section) explicitly selects remote issuer discovery/signatures plus direct native token and authorization entry validation. Current issuer already emits signed unencrypted300-second access tokens with scope `identity.admin` and audience `identity-admin-api`. Introspection/reference substitution is unnecessary.
- **Credentials**: B3 callback captures the access token but intentionally drops it before ticket establishment. Use the existing protected native ticket token-property contract, preserving exact receipt checks and atomic commit. No plaintext/new token table, ID-token forwarding or refresh.
- **Current permission**: The token has no current permission authority. Reuse persisted ordinal role/grant semantics and current session policy; issuance `ProtocolAdmissionProof` is unsuitable because it writes observations and applies login freshness. A narrow rollback-only authority mode preserves global/profile/account lock order and avoids inconsistent separate reads.
- **Catalogue**: Read native application summaries only; no credential fields or product enabled status invented before its lifecycle exists. The real BFF registration is visible in the local demo. Default25/max100 paging comes from the approved API contract; exact bounded search/sort semantics are recorded in contracts before code.
- **Composition**: Existing local demo starts only issuer/BFF/initializer. Add a real API container and corresponding genuine browser/API fixture boundary, including two independent API roots for revocation evidence.
- **Evidence**: Existing feature017 has4,745ordinary+11frontend passes. Preserve its complete identity inventory; new counts are derived from actual discovery/results, never guessed. Existing raw evidence and worktrees remain preserved.
