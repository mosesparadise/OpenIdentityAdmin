# Native client graceful process restart

Scope: feature 011 T005–T009 and required T021/T022 dependencies; B2-CLIENT-01/03 and B2-OPS-01; FR-005/006/009–013 and SC-001/002/004–006. This adds two actual-process provider cases and two private-input provider controls. It does not activate product BFF authentication.

## Separate native processes

`NativeClientProcessTests` starts a real local HTTPS issuer with the genuine account enrollment/session and fixed registration. A test-only `IdentityPlatform.NativeClient.Driver` process imports separately owned copies of protected synthetic client keys and uses only the least-privilege Sessions runtime connection. It runs the same assertion-free `NativeClientRequest` executor as the existing in-process interoperability tests: actual named native ASP.NET handling, production storage/response ownership, original completion callbacks and the actual HTTP request lifetime. The driver has no issuer bridge or TLS trust override; its PAR/token requests use normal native HTTPS and the inherited test trust configuration.

Process one creates a real challenge. The parent requires the native redirect and one Secure/HttpOnly/SameSite=Lax correlation cookie, plus one independently read Valid state. Only after the process exits completely does the parent authorize through the genuine account issuer. Process two imports the same protected files and completes that callback once. Its actual authentication result must contain the expected subject, no body/redirect and only native correlation-cookie output. Independent issuer reads require exactly two issued token rows with unchanged authorization count; Sessions must contain one Redeemed state. Process three imports again and replays the original callback: exact native `InvalidToken/ID2139`, HTTP 503, no authentication/body/location/cookie, unchanged issuer rows and Redeemed state. The real HTTPS host must observe exactly one PAR and one token send, no failed/redirected sends, and all three observed OS process generations must differ.

The private result is written only after the request callbacks, child/root services and imported credentials finish disposal. The parent requires the result frame, successful process exit, stdout EOF, empty stderr and exact process-group termination before returning each result or starting the next child. Existing governance process ownership is extracted into reusable `DriverProcess`; original governance controls, 1,024-character bound, process-generation checks, hard stop, stream drain and deadlines are retained. Only the fixed native-client executable role uses a 65,536-character frame bound. No caller supplies an arbitrary executable or command.

This proves graceful OS-process replacement and state/key persistence. It does not simulate a forced crash, deployed browser/BFF hosting, elapsed-time expiry or production restart orchestration. The parent supplies the same explicit synthetic UTC policy snapshot to each child; monotonic timestamps and timers remain real. Existing production operation/request deadlines are unchanged. The outer test-process lifetime remains 60 seconds with the existing 10-second drain bound. Native driver logs are disabled, so this case does not claim log-redaction evidence; the separate completion/logging suite owns that claim.

## Private input and adversarial controls

Synthetic connections, key-file passwords and callback/cookie values travel only through redirected private stdin/stdout, never command-line arguments or diagnostic text. Input is byte-bounded, depth-bounded, closed-schema and recursively duplicate-checked; arrays and trailing frames are rejected before composition. Only known providers, the exact client/callback profile, a loopback HTTPS issuer and six explicit protected-credential settings are accepted. Failure output contains only finite stage/category values. The input byte buffer is cleared after processing; no general memory-erasure claim is made for managed strings.

The malformed-frame controls use an otherwise complete valid input. Its uniquely named, independently confirmed absent key file causes failure at the Request stage before persistence is registered or accessed. Changing only a duplicate valid Provider member or appending another frame must fail at the earlier Input stage. This positive stage control prevents a missing-required-field failure from falsely proving framing protection. All failures require exit 2, bounded private framing and complete process/stream cleanup. Independent security review found the original incomplete controls insufficient; the complete control and exact-stage assertions resolve that finding. Architecture review's missing successful callback-cookie check is also resolved by reusing the existing safe prefix assertion.
