- Retained PAR: seed 9,999 Redeemed request rows. Actual PAR creates retained row 10,000; the next request must deny with unchanged rows. Redeemed seed rows do not consume the live-request ceiling. Both PAR cases then authorize and fully exchange the accepted reference with independently validated native code/access/ID artifacts.
- Authorization: prepare two genuine PAR references and seed 1,999 Valid ad-hoc authorizations. Actual authorize creates the final code/authorization at 2,000. Authorizing the other reference must return the exact fixed native temporary-unavailability callback, consume that PAR durably, and create no credential/authorization rows. The accepted code still exchanges successfully.
- Total native tokens: prepare two actual codes plus another PAR and seed recent native token rows to leave exactly two slots. A real exchange creates its access and ID entries at 20,000 total. Subsequent PAR, authorize and token creation each deny without changing the retained count; earlier PAR/code consumption remains Redeemed. This tests all three issuance entry points against the shared total cap.

These are real native HTTP-pipeline requests using independent service roots, not a claim that the in-process issuer adapter is network transport. Existing component controls already prove concurrent reservation, partial creation, dependency-aware cleanup and unknown-commit behavior; those implementations/oracles are preserved rather than duplicated.

## Restored-row consequences and explicit invalidation

`NativeRestoreConsequenceTests` adds one case/provider. A real native client challenge and actual account authorize produce a genuine callback. `NativeTokenSnapshot` privately captures the exact Valid code row and Valid Sessions callback-state row, including every EF scalar property: payload, identifiers, shadow foreign keys, timestamps and concurrency values. The first callback authenticates and issues exactly two token rows. Ordinary replay on an independent client root must fail at native redeemed-state validation without another token send.

While all operations are quiescent in disposable databases, the fixture requires both current rows to be Redeemed and reinstates only those captured images under their actual owning profile/state locks. Independent scopes compare every scalar field to the snapshots, not merely the status. A fresh client root submits the same genuine callback/correlation cookie and must authenticate again, issuing exactly two more token rows. This intentionally unsafe positive control demonstrates why restoring consumed credentials without invalidation is dangerous; retained clocks/credentials alone do not prevent resurrection.

The fixture restores those exact images a second time, then disables the fixed registration, invokes actual `JourneyLogout` for the current account session, uses native token/authorization managers to revoke the fixed application's artifacts/grants, and revokes the resurrected Sessions state. No request resumes during these sequential test-owned changes. A newly constructed client root must reject the original callback with exact `InvalidToken/ID2019`, HTTP 503, no authentication/body/location/cookie and no further token send. Independent persisted queries require the profile disabled, session revoked, all scoped native token/authorization rows Revoked, and both captured rows Revoked; retained counts cannot grow.

This demonstrates isolated row resurrection and explicit quiescent invalidation. It does not execute a provider backup/restore, claim crash consistency, restore an entire database, test every possible cross-store restore point, or implement an audited production recovery procedure. Early state rejection is the causal callback-denial boundary; other invalidations are independently verified persisted effects, not individually isolated denial proofs. The [operator runbook](../../docs/operations/administrator-native-client.md) still requires isolation and separately reviewed invalidation before authorized re-enablement, and still records missing production automation. Raw snapshots and synthetic credentials never enter diagnostics or committed evidence.
